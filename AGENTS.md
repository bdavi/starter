# AGENTS.md

Instructions for AI coding agents working in this repo. See [ADR-00002](./docs/adrs/00002-ai-agent-context-files.md) for why this file exists and how it relates to the ADR log.

## What this repo is

A reusable starter template for building SaaS products. Full purpose and design goals: [ADR-00000](./docs/adrs/00000-purpose-and-goals.md).

## Layout

This is a monorepo ([ADR-00001](./docs/adrs/00001-monorepo-vs-polyrepo.md)):

- `docs/adrs/` — Architecture Decision Records, in chronological order. Read the relevant ones before making structural changes.
- `apps/web` — customer-facing product (Next.js, App Router, colocated backend). Scaffolded via `@nx/next`: Jest for unit tests, Playwright for e2e (`apps/web-e2e`), ESLint, Tailwind CSS v4 (`@import "tailwindcss"` in `src/app/global.css`, config in `postcss.config.mjs`). See [ADR-00003](./docs/adrs/00003-web-app-language-and-architecture.md).
- `apps/worker` — background/async job processor (TypeScript) — not yet scaffolded.
- `apps/admin` — internal admin tooling, separate deployable from `apps/web` — not yet scaffolded.
- `apps/mobile` — planned, not yet built: React Native via Expo, once a native app is actually needed.
- `packages/config` — a reusable Zod-backed validated-env-getter helper (`createEnvGetter`), not an aggregator of every env var — see [ADR-00013](./docs/adrs/00013-environment-config-scoping.md). Scaffolded.
- `packages/db` — Postgres + Drizzle: client, schema, migrations. Scaffolded.
- `packages/auth` — authentication (Better Auth). Scaffolded.
- `packages/domain`, `packages/schemas`, `packages/queue`, `packages/email`, `packages/ui` — remaining shared logic; apps stay thin orchestration shells around these. See [ADR-00004](./docs/adrs/00004-monorepo-app-and-package-structure.md) for what each holds and why.

## Status

Stack decided: TypeScript throughout, pnpm workspaces + Nx for the monorepo, Next.js for `apps/web` (see [ADR-00003](./docs/adrs/00003-web-app-language-and-architecture.md), [ADR-00004](./docs/adrs/00004-monorepo-app-and-package-structure.md), [ADR-00005](./docs/adrs/00005-monorepo-build-tooling.md)).

**The workspace is scaffolded**: root `package.json`, `pnpm-workspace.yaml`, and Nx (`nx.json`) are set up. Run tasks via `pnpm nx <command>` (not a global `nx` install). **`apps/web` is scaffolded** (Next.js, Jest, Playwright, ESLint, Tailwind CSS v4) — build/lint/test all pass. **`packages/config`, `packages/db`, `packages/auth` are scaffolded and wired together** (ADR-00011, ADR-00012, ADR-00013) — see their nested `AGENTS.md`/`README.md` files, especially the `moduleResolution` gotcha noted in each (Nx's library generator's `nodenext` default breaks Next.js's `transpilePackages` resolution; these three deliberately override it back to `bundler`). Env vars are scoped per-package, not centralized — `packages/db` validates `DATABASE_URL` itself, `packages/auth` validates its own secret/URL itself, `packages/config` only provides the shared `createEnvGetter` helper (ADR-00013). This is enforced, not just convention: `eslint-plugin-n`'s `no-process-env` rule blocks direct `process.env` access anywhere except the `createEnvGetter` implementation itself and test files — a new package needing config must add its own `env.ts` using that helper, not read `process.env` directly (see `docs/scanning-tools.md`). `apps/worker`, `apps/admin`, `apps/mobile`, and the remaining `packages/*` do not exist yet. Do not assume or invent build/test/lint commands for a specific app/package until it's actually been scaffolded; check `pnpm nx show projects` before claiming a command exists.

This repo defaults to a **maximalist linting strategy** (see [ADR-00014](./docs/adrs/00014-maximalist-linting-for-ai-agent-development.md)): when a convention is mechanically checkable, add the check rather than relying on it being remembered — this is a deliberate consequence of most of this repo being built by AI agents, whose session-to-session memory doesn't work like a human's. Two recent examples: `@nx/enforce-module-boundaries` now actually enforces that nothing — neither a package nor another app — may depend on a `type:app` (ADR-00004's "apps are thin" principle plus ADR-00003's "an app's internals aren't another app's public contract," both previously just stated); **Syncpack** (`pnpm run deps:check`, blocking in `ci.yml`) catches cross-package dependency-version drift, paired with pnpm workspace **catalogs** (`pnpm-workspace.yaml`'s `catalog:` field) as the prevention-side mechanism for dependencies genuinely shared across packages (`zod` is the first entry — add a new one only once a dependency is actually shared by more than one package/app, not preemptively).

Nx's caching is content-hash-based and does work correctly locally (verified: identical content reliably cache-hits). `lint` and `test` cache reliably across runs. `build` has shown occasional extra rebuilds in some multi-command sequences during testing that weren't cleanly reproducible or root-caused — performance/DX only, not a correctness issue. Worth another look if it becomes a real CI-speed problem, not urgent otherwise.

**Tried and reverted: a self-managed `actions/cache` step caching `.nx/cache` in `ci.yml`, to avoid recomputing `nx affected` tasks from zero on every CI run.** Doesn't actually work on GitHub-hosted runners, for a real reason, not a config mistake worth retrying: Nx 23's default cache is a SQLite db that lives in `.nx/workspace-data` (not `.nx/cache` — caching only the latter means the db recording "these artifacts are valid" never travels with them), and more fundamentally, that db scopes trust to a machine ID (a hash of `/etc/machine-id`, an anti-cache-poisoning safeguard — see https://nx.dev/troubleshooting/unknown-local-cache), which is different on every ephemeral GitHub Actions runner. Restoring artifacts "from another machine" is exactly what Nx refuses to trust by design, producing `NX Unrecognized Cache Artifacts` every run with no actual cache hits. This is why Nx's own docs steer CI caching toward Nx Cloud (Nx Replay) instead — a different trust model (signed URLs, immutable artifacts) built specifically to be safe across machines. If CI speed becomes a real problem, Nx Cloud is the path that actually works here, not another variation on `actions/cache`.

Linting/formatting/security scanning strategy implemented per [ADR-00009](./docs/adrs/00009-linting-formatting-and-security-scanning.md): ESLint (sonarjs/import-x/security plugins) + Prettier + prettier-plugin-tailwindcss are wired in and passing; `lefthook.yml` has pre-commit (lint, format-autofix, Gitleaks) and pre-push (typecheck) hooks, tested directly (not just written); `knip.json` is tuned to a clean baseline (warn-only, not a gate); `pnpm run health` runs the repo health script (Knip + `pnpm audit` + osv-scanner + `scripts/churn-vs-complexity.sh` — files that are both frequently changed and complex, the same "hotspot" technique behind CodeScene/code-maat, done here with git history + ESLint's own `complexity` rule rather than a new runtime dependency; also runnable standalone via `pnpm run hotspots`). `.github/workflows/ci.yml` (PR CI) and `repo-health.yml` (scheduled) exist and `ci.yml` has been exercised by real pushes (caught two real bugs — a missing Nx task `dependsOn` and a build-time env var gap — see the convention below about clean-checkout verification). `renovate.json` exists, passes Renovate's own validator, and the GitHub App is installed. Gitleaks is a required local install (like lefthook) — the pre-commit hook hard-fails without it, by design.

Every action ref in `ci.yml`/`repo-health.yml` is SHA-pinned, not tag-referenced (`@v6` etc.) — see [ADR-00010](./docs/adrs/00010-github-actions-supply-chain-hardening.md) for why this matters (mutable tags are a real supply-chain attack surface) and how it's kept correct: a blocking `zizmor` CI job re-verifies pinning (and a few other Actions-specific security properties) on every push/PR, and `renovate.json`'s `helpers:pinGitHubActionDigestsToSemver` preset keeps the pins current via normal Renovate PRs rather than manual re-resolution. When adding or editing a workflow step that references a third-party action, pin it the same way — don't add a bare `@vN` tag; `zizmor` will fail the build if you do. `lefthook.yml`'s pre-push hook also runs `zizmor` locally (skips gracefully if it isn't installed) for faster feedback than waiting on CI — but it isn't the enforcement boundary. **Known gap, not yet closed**: `ci.yml`'s `main`/`security-warn` jobs don't `needs: zizmor`, so within a single CI run a reverted pin could still execute in those jobs before `zizmor` fails — closing that (job dependency + branch protection requiring the check) is deferred, on the user's instruction, to a later pass alongside setting up branch protection.

E2E (ADR-00007's two-tier design): `apps/web-e2e` tests tagged `@critical` run on chromium on every push (`ci.yml`, blocking). The full suite (all tests, all browsers) is part of `pnpm run health`/`scripts/repo-health.sh` — runs locally on demand, and weekly + on-demand in CI via `repo-health.yml` (which installs Playwright's browsers first, then runs the same script). Needs Playwright browsers installed locally (`pnpm exec playwright install`) or it reports that clearly rather than silently doing nothing. Only one test exists so far (a smoke test, tagged `@critical`).

A periodic maintenance review exists per [ADR-00015](./docs/adrs/00015-periodic-maintenance-review.md): [`docs/maintenance-review.md`](./docs/maintenance-review.md) is the tool-agnostic procedure (run `pnpm run health`, summarize open Renovate PRs, review hotspots/TODOs/documentation drift, produce one punch list, never implement anything itself); Claude Code additionally exposes it as `/maintenance-review` (`.claude/skills/maintenance-review/SKILL.md`, manually-invoked only). Each run appends to [`docs/maintenance-log.md`](./docs/maintenance-log.md) — check that file for what was left open last time before assuming a finding is new.

Nested `apps/web/{README,AGENTS}.md` and `apps/web-e2e/{README,AGENTS}.md` exist per the convention below — check those first for anything specific to those apps before assuming root `AGENTS.md` has the full picture.

Required Node and pnpm versions are pinned in `.tool-versions` (the portable format shared by both [asdf](https://asdf-vm.com/) and [mise](https://mise.jdx.dev/) — use whichever you prefer, neither is mandated).

Local dev environment decided (see [ADR-00008](./docs/adrs/00008-local-development-environment.md)): Docker Compose for backing services only — apps run natively via `nx run-many -t dev`, not in containers. **`docker-compose.yml` is scaffolded** (Postgres only so far — note the Postgres 18+ volume-mount gotcha commented directly in that file) and `scripts/db-reset.sh` exists. No combined `pnpm dev` script (Compose + `nx run-many -t dev` in one command) yet, and no Redis/other backing services yet — both real, not-yet-done follow-ups, not decisions.

## Conventions

- Significant technical decisions are recorded as ADRs in `docs/adrs/`, following the template in `docs/adrs/README.md`. If you make or observe a structural/architectural decision, propose an ADR for it rather than leaving it undocumented.
- When writing a new ADR or establishing a new convention (here or in a nested `AGENTS.md`), explicitly consider whether it's mechanically checkable — a lint rule, a config-file constraint, a CI check — rather than relying on the decision being remembered and followed by hand. A convention that's only written down is one bad day away from being silently violated; see [ADR-00013](./docs/adrs/00013-environment-config-scoping.md) + `eslint-plugin-n`'s `no-process-env` rule for the pattern (decision recorded in the ADR, then actually enforced, not just documented). If a real check exists, add it to `docs/scanning-tools.md` in the same commit; if one doesn't exist or isn't worth the cost, say so explicitly in the ADR's Consequences rather than leaving it unstated.
- Default to parity between local/staging/production environments — the 12-factor app "dev/prod parity" principle. Run the same real services locally as in production rather than lighter local-only substitutes; this is already the reasoning behind ADR-00008's Docker Compose approach (real Postgres/Redis locally, not mocks), and it should keep applying as new infrastructure gets added (e.g. running a real OpenTelemetry Collector locally too, not just in production, so redaction/pipeline config is actually exercised before it matters). Pragmatic exceptions are fine when parity has a real, specific cost (e.g. a paid-only third-party dependency with no viable local equivalent) — but that's a deliberate, called-out exception, not the default assumption.
- ADRs are a history, not a current-state view — they don't get rewritten as tools/config change after the fact. [`docs/scanning-tools.md`](./docs/scanning-tools.md) is the current-state counterpart specifically for linting/formatting/security-scanning/CI-supply-chain tooling: what's installed, where it runs, and whether it blocks. When you add, remove, or reconfigure a tool in that category, update that table in the same commit — that's the whole reason it exists instead of making people reconstruct current state by reading every ADR in order.
- Do not run `git commit` (or otherwise create commits) unless the user gives specific direction to do so in that moment. Staging, diffing, and other read-only or reversible git commands are fine.
- Do not run `git push` (to any remote or branch) unless the user gives specific direction to do so in that moment — same rule as committing, and for the same reason: pushing affects shared/remote state, not just this local checkout.
- When committing, evaluate the pending changes first: if they contain several distinct logical changes, split them into separate commits rather than one bundled commit. Generally, commit code, its tests, and its documentation together as a single unit rather than splitting them apart.
- Once `apps/*` or `packages/*` contain real packages, each should get its own `AGENTS.md` and `README.md`. Use the nearest one to the file you're editing — root files are the fallback baseline, package-level ones take precedence for anything package-specific. `README.md` is canonical for facts a human and an agent both need (build/test/run commands, layout); the package's `AGENTS.md` should link to it rather than restating those facts, adding only agent-specific behavioral guidance.
- Documentation is a first-class concern, not an afterthought — see [ADR-00006](./docs/adrs/00006-documentation-strategy.md). Prefer generated documentation over hand-written wherever a generator exists (e.g. OpenAPI from schemas, TypeDoc from code comments, Nx's dependency graph) rather than writing prose that duplicates what the code already states.
- A feature's _value_ (why it exists) is short, hand-written prose; a feature's _behavior_ ("it does X") should be backed by automated acceptance tests, not a prose description — tests can't silently drift out of sync with the code the way descriptions can. See [ADR-00007](./docs/adrs/00007-testing-and-qa-strategy.md). Treat a feature as incomplete if it has one but not the other.
- When a commit touches many lines without changing meaning (reformatting, mass renames, lint-fix sweeps), add its hash to `.git-blame-ignore-revs` so `git blame` keeps pointing at the last meaningful change. This only takes effect per-clone via `git config blame.ignoreRevsFile .git-blame-ignore-revs`.
- Commit messages follow the classic 50/72 style (see `.gitmessage`): imperative-mood subject ≤50 chars, blank line, body wrapped at ~72 chars explaining why not what. This only takes effect per-clone via `git config commit.template .gitmessage`.
- When creating a new application or other code structure that has an official generator/scaffolding CLI, prefer running that tool over hand-writing the files. For example, scaffold a new Next.js app with `pnpm create next-app` rather than creating its files manually — generators track upstream conventions and config more accurately than reproducing them by hand. After scaffolding, make whatever changes are needed on top of the generated result.
- If a requested task is really something a script could do — especially one that's repetitive, iterative, or likely to be run again (a data migration, a bulk rename, a repeated audit/check) — prefer writing a small, reusable script (bash or otherwise) over doing the work by hand step by step. If it seems likely the task will come up again, ask the user whether the script is worth keeping around rather than treating it as disposable.
- A long-lived local working directory can accumulate gitignored build artifacts (`.next/`, etc.) that mask real failures — a rule that legitimately fails on a genuinely clean checkout (fresh clone, or CI, which has never run a build) can still pass locally simply because a stale artifact from an earlier session is still sitting on disk, even with `--skip-nx-cache`. Before trusting a "local passes, CI fails" result as a real environment/config difference, reproduce in an isolated fresh clone (`git clone` to a temp dir, fresh install, same base/head) before concluding it's not reproducible — don't assume a clean local run proves the code is actually clean.
