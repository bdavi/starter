## Agent-specific notes

- Tagged `type:app` for Nx's module-boundary rule (`@nx/enforce-module-boundaries` in the root `eslint.config.mjs`). It's enforced now, not just declared: no `type:lib` project (`packages/config`/`db`/`auth`) can depend on this app, and this app can't depend on another app either (e.g. a future `apps/admin`) — only on `type:lib` projects. Verified nothing currently relies on app-to-app: `apps/web-e2e`'s `implicitDependencies: ["web"]` looks like a code dependency but isn't — it's Nx task-graph only, Playwright talks to `web`'s dev server over HTTP, not via import. Per ADR-00003, this app's internal data-loading functions are not a public contract another app should ever import directly — if two apps need to share something, it belongs in a package. Finer-grained boundaries between individual packages aren't enforced yet.
- `next-env.d.ts` is auto-generated by Next.js ("This file should not be edited") and is gitignored, not committed — its content used to flip between a dev-mode and build-mode variant depending on whichever of `next dev`/`next build` last ran, which caused constant spurious diffs. It's now produced by a dedicated `typegen` Nx target (`next typegen` — generates route types without a full build), which `lint` and `typecheck` both `dependsOn`, so it's regenerated automatically and deterministically before either runs, on a fresh checkout or otherwise. The root ESLint config still excludes it from `import-x/no-unresolved` as defense in depth (e.g. an IDE invoking `eslint` directly, bypassing Nx's dependency graph) — don't remove that exclusion without understanding why it's there.
- This app's `typecheck` target is a custom `package.json` override (`tsc --noEmit -p tsconfig.json`), not Nx's plugin-inferred default — and a project-level target override fully replaces the inferred one rather than merging into it, so it does NOT automatically pick up the `dependsOn: ["^typecheck"]` edge the `@nx/js/typescript` plugin normally wires in. That edge matters here specifically: `apps/web/tsconfig.json` has a real TS project reference to `packages/auth`, and plain `tsc --noEmit` (unlike `tsc --build`) doesn't build referenced projects — it only reads whatever `dist/*.d.ts` they already have on disk, failing with TS6305 if that output is missing or stale. `dependsOn` explicitly lists `"^typecheck"` (alongside `"typegen"`) to guarantee `packages/auth` (and transitively `db`/`config`) have already run their own `tsc --build` and produced fresh `dist/*.d.ts` first. This broke in CI/a fresh clone before it was caught: a long-lived local working directory accumulates stale-but-present `dist/` output from many earlier `nx build`/`nx typecheck` runs, which silently masks the missing dependency edge — always verify Nx target/dependsOn changes like this against a clean clone (the isolated-fresh-clone convention in the root `AGENTS.md`), not just a local run. If any other app ever gets a custom target override that consumes another project's build output, check `pnpm exec nx show project <name> --json` for the plugin-inferred version first and carry forward its `dependsOn`.
- `src/app/**` files (pages, layouts, routes) are discovered by Next.js's App Router file-based routing, not imported explicitly anywhere. Don't assume a file is dead code just because nothing references it — check whether it follows the routing convention first (Knip's config already accounts for this).
- No real business logic exists yet — don't build on assumptions about what this app "does" beyond what's in the code right now.
- `next.config.js`'s `transpilePackages` must list every internal `@starter/*` workspace package this app actually imports (currently `config`, `db`, `auth`) — omitting one produces a `Module not found` error specifically in the RSC/server bundle (client-only routes can appear to work fine, which is a misleading signal). See [ADR-00011](../../docs/adrs/00011-database-technology.md)'s Consequences section for the full story.
- No `proxy.ts`/`middleware.ts` exists here on purpose — Next.js 16 renamed `middleware` to `proxy` and now explicitly discourages database-backed checks in that layer. Session protection for a route (see `src/app/dashboard/page.tsx`) happens via `auth.api.getSession()` called directly in that route's own Server Component. See [ADR-00012](../../docs/adrs/00012-authentication-architecture.md).
