# AGENTS.md — services/otel-collector

See [README.md](./README.md) for what this is, its stack, and its commands — not repeated here.

## Agent-specific notes

- This is the first non-TypeScript component in the repo (Go, built via OCB). It does **not** join Nx's task graph — don't add it to `nx.json`, don't expect `pnpm nx <target>` to work here, don't expect Renovate to track `manifest.yaml`'s pinned versions the way it tracks `package.json`. See [ADR-00019](../../docs/adrs/00019-non-ts-service-pattern.md).
- `manifest.yaml` pins every component's version to match the OCB/core/contrib version exactly (currently `v0.157.0`). Bumping one without the others is a common, real source of build breakage — verify with `builder --config manifest.yaml` before assuming a bump is safe.
- Component names in `config/*.yaml` don't always match the module name in `manifest.yaml` — e.g. the `hostmetricsreceiver` Go module registers as `host_metrics` in config (not `hostmetrics`, which is a deprecated alias that logs a warning), and `otlphttpexporter` registers as `otlp_http` (not `otlphttp`). If you add a component, run `./dist/starter-otelcol components` after building to see its actual registered name before writing config against a guess.
- OTTL conditions (used in `filter/health_checks`) require an explicit context prefix — `span.attributes[...]` for `trace_conditions`, `log.attributes[...]` for `log_conditions`, not a bare `attributes[...]`. `./dist/starter-otelcol validate --config <file>` catches this at build time; use it before assuming a config change is correct.
- The `redaction` processor's `hmac_key` must be ≥ 32 bytes or the Collector refuses to start — validated, not just documented; don't shorten the generation command in README.md without checking this still holds.
- The Sentry exporter (`exporter/sentryexporter`) needs `url` + `org_slug` + `auth_token` (a real Sentry API token with `project:read`/`org:read` scope) — not a DSN. Routes by the `service.name` resource attribute to a Sentry project slug; if that attribute is missing, data for that resource is silently dropped with a warning, not an error — worth remembering if Sentry output ever looks incomplete.
- `test/verify.sh` starts a real Collector process and multiple `telemetrygen` subprocesses. If you're debugging it and need to kill a stray Collector process by hand, use `pkill -9 -x starter-otelcol` (exact process-name match), **not** `pkill -f` — a `-f` (full-command-line) match can self-match whatever wrapper is currently running your own shell command and kill the wrong thing, since `-f` matches substrings across the entire command line, including in shells that echo/eval the command being run.
- Health-check telemetry is dropped by **two different processors depending on signal type** (ADR-00022) — don't assume one processor covers both. **Traces** use `tail_sampling` (a `drop` + `always_sample` policy pair, matched on `http.target`) because `filterprocessor` only drops the individual span that matches, not the whole trace — verified via real multi-span `apps/web` traffic that this left orphaned sibling spans behind in Tempo even when the condition matched something. **Logs** still use `filterprocessor` (`log_conditions`, matched on `http.route`) — a log record has no multi-span structure to preserve, so per-record matching is fine there. If `apps/web`'s health-check route ever moves, update `config/collector.yaml`, `config/collector.test.yaml`, and `test/verify.sh`'s `HEALTH_ROUTE` together — and remember the traces path keys on `http.target`, not `http.route` (Next.js's auto-instrumentation doesn't reliably set `http.route` on the root span; `http.target` was the one attribute consistently present across every case observed).
- `tail_sampling` policies matter in a specific way: a `drop` policy is a hard veto, but with **no other policy in the list, everything gets dropped by default**, not just what the `drop` policy targets — per the processor's own README's documented decision flow, a trace needs an explicit "sample" decision from _some_ policy to survive. `sample_everything_else: always_sample` is required alongside `drop_health_checks`, not optional/redundant.
- `tail_sampling` buffers each trace for `decision_wait` before making a keep/drop decision (5s in the real config, 1s in the test config) — traces take noticeably longer to reach Tempo/Sentry/spanmetrics than before this was added. In practice, budget ~10-15s end-to-end (decision_wait + export + backend indexing) before treating a trace's absence from a query as a real signal, not just normal latency.
- `tail_sampling` requires every span of a given trace to reach the _same_ Collector instance (documented in its own README) — genuinely incompatible with a future topology where a trace spans multiple of this repo's own services, each behind its own "agent per service" Collector (ADR-00018's production shape). Not a live problem with only one app and no cross-service trace propagation; a real thing to revisit before that changes (ADR-00022's Consequences).
