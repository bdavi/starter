# AGENTS.md — packages/observability

See [README.md](./README.md) for what this package is and its commands — not repeated here.

## Agent-specific notes

- **`logger-registry.ts` and `tags.ts` store their state on `globalThis` (keyed by `Symbol.for(...)`), not in a module-scoped variable.** This isn't stylistic — a module-scoped `let active` broke in real testing: apps/web's `next.config.js` puts this package in `transpilePackages`, and Turbopack compiles each of the package's entry points (`instrumentation.ts` calling `setup()` vs. an individual route handler calling `logger.debug()`) into separate chunks that don't share module state, even though it's the same file on disk. The symptom was silent, not a crash — `setup()` ran successfully and `registerActiveLogger()` was called, but a route handler's `logger.*()` calls still fell through to the console fallback, because it was reading a _different_ module instance's `active` variable. Diagnosed by giving the module a random instance ID at load time and logging it on both register and read — they were different IDs in the same process. `Symbol.for()` (not a plain module-scoped `Symbol()` or string key) is what makes this fix work across separate module instances: it returns the identical symbol value regardless of which compiled copy of the file is asking for it, so they all land on the same `globalThis` slot. If you add another piece of module-scoped mutable state to this package, it needs the same treatment, not a plain `let`/`const`.
- Verified end-to-end (not just unit-tested) that the `pino-opentelemetry-transport` worker thread actually works under Next.js/Turbopack bundling: built and ran `apps/web` in real production mode (`next build && next start`), pointed it at a real Collector instance (test config, file exporter), hit `/api/health`, and confirmed the log record actually arrived (`process.command` in the output showed the real `thread-stream/lib/worker.js` worker). This was a real, previously-unverified risk (worker threads spawned by bundled/transpiled code are a common source of "works in tests, breaks in a real bundler" bugs) — don't assume it still works after changing `next.config.js`'s `serverExternalPackages` or this package's own dependency list without re-running the same check.
- `next.config.js` cannot `import`/`require()` `@starter/observability` or `@starter/observability/node` directly — it runs under plain Node before any bundler exists, and those entry points have their own relative imports (extensionless, per this repo's `moduleResolution: "bundler"` convention) that plain Node can't resolve without one. `./external-packages` is a separate, dependency-free entry point specifically so `next.config.js` has something it _can_ load directly — verified empirically (`node -e "require('@starter/observability/external-packages')"` from `apps/web` succeeds; the same test against `./node` fails with `Cannot find module`). Don't merge `external-packages.ts`'s export back into `node.ts`'s barrel.
- `moduleResolution` is deliberately `bundler` (inherited from root), not Nx's generator default of `nodenext` — see `packages/config/AGENTS.md` for the full reasoning.
- `setup.ts`'s `pino()` call passes `resourceAttributes`/exporter config directly to the `pino-opentelemetry-transport` options, duplicating values also passed to `NodeSDK`'s `resource` — this isn't accidental duplication. `pino.transport()` runs its target in a separate worker thread, which can't share JS object references with the main thread; the transport needs its own fully-serializable config.
- `@opentelemetry/auto-instrumentations-node`, `@opentelemetry/instrumentation-pino`, and `@sentry/node` are pinned to exact (non-`^`) versions in `package.json`, not the usual caret range — they (and/or their transitive deps) were hitting `pnpm-workspace.yaml`'s `minimumReleaseAge` (7-day) supply-chain gate at the versions Renovate would otherwise pick. Pinned to the newest version of each that's already past that window. Don't casually bump these back to `^` without checking `npm view <pkg> time --json` against the current date first.
- `protobufjs` (a transitive dep of `@opentelemetry/sdk-node`'s unused gRPC exporters — this package only uses OTLP/HTTP) is set to `allowBuilds: false` in `pnpm-workspace.yaml`, not left unset — its postinstall script is a harmless version-mismatch warning, not a native compile step, so there's nothing to gain by allowing it to run and it would otherwise block every `pnpm install` with an unresolved approval prompt.
